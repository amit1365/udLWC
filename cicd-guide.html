What Is CI/CD

CI/CD is automation that runs every time you push or merge code. Instead of you manually running tests and deploying, a machine does it automatically and reports pass or fail.

CI — Continuous Integration

  • Runs when you push a branch or open a PR
  • Checks: is this code clean and working?
  • Runs lint, format checks, unit tests
  • Blocks the PR if anything fails
  • Prevents broken code from reaching main

CD — Continuous Deployment

  • Runs when you merge a PR into main
  • Does: ship this code to the live environment
  • For Salesforce: deploys to your org
  • No manual deployment needed
  • Every merge = automatic deploy
📌
One line each

CI = test the code when pushed to GitHub — "is it good enough to merge?"
CD = deploy the code when merged to main — "ship it to the Salesforce org."

How It Works — GitHub Actions

GitHub has a built-in CI/CD engine called GitHub Actions. It is free for public repos. No third-party tools needed. It works by reading a file you create in your repo.

How GitHub Actions Works

You create a .yml file inside .github/workflows/ in your repo. GitHub reads this file automatically. When a trigger happens (a push, a PR, a merge), GitHub spins up a fresh cloud machine, runs all the steps you defined in the file, and reports green or red on your PR. The machine is deleted after the job finishes.

# What lives where:

Your repo on GitHub
  └── .github/
        └── workflows/
              ├── ci.yml       ← CI: runs on every branch push / PR
              └── deploy.yml   ← CD: runs on every merge to main

# GitHub reads these files automatically — no setup on GitHub's side needed

What is in a workflow file:

name: CI

on:                          # WHEN does this run?
  push:
    branches-ignore: [main]  # on every branch push except main
  pull_request:
    branches: [main]         # on every PR targeting main

jobs:
  lint-format-test:
    runs-on: ubuntu-latest   # GitHub spins up a fresh Ubuntu machine

    steps:
      - uses: actions/checkout@v4         # download your code onto that machine
      - uses: actions/setup-node@v4       # install Node.js
        with:
          node-version: '18'
          cache: 'npm'

      - name: Install dependencies
        run: npm install

      - name: Run ESLint
        run: npm run lint

      - name: Check Prettier formatting
        run: npm run prettier:verify

      - name: Run Jest tests
        run: npm test

What Happens at Each Stage

Trace exactly what happens from the moment you push code to the moment it is live in your Salesforce org.

💻
You push a branch Your Machine

You finish coding and push your feature branch to GitHub.

git push origin feature/my-new-lwc
⚡
GitHub Actions triggers automatically GitHub Cloud

GitHub sees the push, reads your .github/workflows/ci.yml file, and spins up a fresh Ubuntu machine in the cloud. This takes about 10–15 seconds to start.

📥
Machine downloads your code GitHub Cloud

Step 1 of your workflow runs — actions/checkout clones your branch onto that machine.

🔧
Dependencies installed GitHub Cloud

npm install runs — installs ESLint, Jest, Prettier and everything in your package.json.

🔍
ESLint runs GitHub Cloud

Checks all your LWC JavaScript files for errors, bad patterns, and rule violations. If any file has an error — the whole CI job fails here.

npm run lint
✨
Prettier check runs GitHub Cloud

Checks that all files (JS, HTML, CSS, Apex, XML) are formatted correctly. Does not auto-fix — just reports what is wrong. If formatting is off — CI fails.

npm run prettier:verify
🧪
Jest tests run GitHub Cloud

All test files in __tests__/ folders are executed. Any failing test fails CI.

npm test
📊
Result reported on your PR GitHub Cloud

GitHub shows the result at the bottom of your Pull Request. Green = all passed. Red = something failed with the exact error shown.

✅ Lint, Prettier, Jest — passed in 1m 24s ❌ Lint, Prettier, Jest — ESLint: 2 errors in quizApp.js
🔀
You merge the PR Manual — GitHub website

If CI is green, you click "Merge pull request" on GitHub. If CI is red, the merge button is blocked until you fix and push again.

🚀
CD triggers — deploy to Salesforce GitHub Cloud

Your deploy workflow detects the merge to main, authenticates to your Salesforce org using stored secrets, and runs the deployment. Your LWC is now live.

sf project deploy start --source-dir force-app

What Lives Where

ItemWhere it livesWho can see it
Your code files GitHub (cloud) Public — anyone
.github/workflows/*.yml GitHub (cloud, inside your repo) Public — anyone can see the file
GitHub Actions runner machine GitHub's cloud servers Nobody — temporary, deleted after job
Secret names (SF_CLIENT_ID etc.) GitHub Settings → Secrets Anyone can see the name, not the value
Secret values (actual credentials) GitHub encrypted storage Nobody — not even you after saving
CI/CD logs (what ran, output) GitHub Actions tab Public on public repos
Your Salesforce org Salesforce cloud Only authenticated users
✅
Secrets are safe

Even though your .yml file is public, nobody can see your actual credential values. GitHub injects them only at runtime inside the private job machine. They never appear in logs — GitHub masks them with ***.

GitHub Secrets — Storing Credentials Safely

You never put passwords or credentials directly in your code or workflow file. GitHub Secrets is the secure way to store them.

How to add a secret

Go to your repo on GitHub → Settings → Secrets and variables → Actions → New repository secret → enter name and value → Save. The value is encrypted immediately and can never be read back.

// Secrets needed for Salesforce CD deployment
Secret NameWhat it holds
SF_CLIENT_ID Consumer key from your Salesforce Connected App
SF_USERNAME Your Salesforce org username (email)
SF_PRIVATE_KEY Private key for JWT authentication 
# In your workflow file you reference secrets like this:
# The actual values are NEVER written in the file

- name: Authenticate to Salesforce
  run: |
    sf org login jwt \
      --client-id ${{ secrets.SF_CLIENT_ID }} \
      --username ${{ secrets.SF_USERNAME }} \
      --jwt-key-file server.key \
      --instance-url https://login.salesforce.com

# Anyone reading your .yml sees:  ${{ secrets.SF_CLIENT_ID }}
# GitHub injects:                 your-actual-consumer-key-value
# In logs it shows:               ***

How to Set It Up — Step by Step

PHASE 1 — CI Setup (do this first)

1️⃣
Create the workflows folder in your repo mkdir -p .github/workflows
2️⃣
Create the CI workflow file

Create .github/workflows/ci.yml with the lint + prettier + test steps shown in Section 3.

3️⃣
Commit and push it git add .github/workflows/ci.yml git commit -m "Add GitHub Actions CI workflow" git push origin your-branch
4️⃣
Enable branch protection on GitHub

GitHub repo → Settings → Branches → Add rule for main

☑ Require a pull request before merging
☑ Require status checks to pass before merging → select your CI job
☑ Require branches to be up to date before merging

PHASE 2 — CD Setup (after CI is working)

1️⃣
Create a Connected App in Salesforce

Salesforce Setup → App Manager → New Connected App → enable OAuth → generate certificate. This gives you a Consumer Key (Client ID).

2️⃣
Store credentials as GitHub Secrets

Add SF_CLIENT_ID, SF_USERNAME, SF_PRIVATE_KEY in GitHub repo Settings → Secrets.

3️⃣
Create the deploy workflow file

Create .github/workflows/deploy.yml that triggers on merge to main, authenticates to Salesforce, and runs sf project deploy.

4️⃣
Test it — merge a PR and watch the deploy

After merging, go to the Actions tab on GitHub. You will see the deploy job running in real time with logs for every step.

Your Complete Developer Loop With CI/CD

// every feature — from idea to live in org

# 1. Start the feature (local)
git checkout main
git pull origin main
git checkout -b feature/my-new-lwc
# 2. Build and commit (local)
// write your LWC code...
git add force-app/main/default/lwc/myNewLwc/
git commit -m "Add myNewLwc component with event handling"
# 3. Push to GitHub — CI starts automatically
git push origin feature/my-new-lwc
// GitHub Actions starts running lint + prettier + tests
# 4. Open PR on github.com (manual)
// Go to github.com/amit1365/udLWC
// Click "Compare & pull request" → Create pull request
// Watch CI result at the bottom of the PR
# 5. If CI fails — fix and push again
// Read the error in GitHub Actions tab
// Fix the issue locally
git add . && git commit -m "Fix lint error in myNewLwc"
git push origin feature/my-new-lwc
// CI reruns automatically
# 6. CI green → merge on github.com (manual)
// Click "Merge pull request" on GitHub
// CD triggers automatically → deploys to Salesforce org
# 7. Clean up (local)
git checkout main
git pull origin main
git branch -d feature/my-new-lwc
