What Is What

Git

A tool installed on your local machine that tracks every change you make to your code. It saves snapshots (commits) of your files over time so you can go back to any previous version. Works completely offline.

GitHub

A cloud platform (website) where you store your Git repository online. It is the backup and collaboration layer. It also provides Pull Requests, code review, and CI/CD (GitHub Actions). GitHub is NOT Git — Git is the tool, GitHub is the hosting service.

Repository (Repo)

A folder that Git is tracking. It contains all your project files plus a hidden .git folder where Git stores the entire history of every change ever made.

Without Git

  • quizApp_v1.js
  • quizApp_v2.js
  • quizApp_final.js
  • quizApp_final_ACTUAL.js
  • No way to collaborate cleanly

With Git

  • quizApp.js (just one file)
  • Git stores every version internally
  • Go back to any point in history
  • Multiple people work without conflict

The Three Zones of Git

Every file in your project lives in one of three zones at any given time. Understanding this makes every Git command make sense.

Working Area

Where you write and edit your code. Just your normal files on disk.

edit files
git add
→

Staging Area

A holding area. You choose which changed files go into the next commit.

git add file.js
git commit
→

Git History

Permanent saved snapshots. Every commit lives here forever locally.

git commit -m ""
💡
Why does staging exist?

You might change 5 files but only want to commit 2 of them right now. Staging lets you choose exactly what goes into each commit, keeping commits focused and clean.

# Example: you changed 3 files but only want to commit 2
# Changed files:
#   quizApp.js                ← finished, ready
#   SearchAccountsController  ← finished, ready
#   searchAccounts.js         ← half done, NOT ready

git add quizApp.js
git add SearchAccountsController.cls
# searchAccounts.js is NOT added — left out of this commit

git commit -m "Fix score bug and casing bug"
# Only quizApp.js and SearchAccountsController.cls are saved

Commit vs Push — Key Distinction

git commit  LOCAL MACHINE ONLY

  • ✦ Saves a snapshot to your local Git history
  • ✦ GitHub has NO idea this happened
  • ✦ Works completely offline
  • ✦ Like hitting Save with a description
  • ✦ Can do many commits before pushing

git push  GOES TO GITHUB

  • ✦ Uploads your commits to GitHub
  • ✦ Requires internet connection
  • ✦ Sends ALL unpushed commits at once
  • ✦ Like uploading your saved file to cloud
  • ✦ Your work is now backed up online
# You can commit many times, push once at the end
git commit -m "Add question list"        ← local only
git commit -m "Add score calculation"    ← local only
git commit -m "Add reset button"        ← local only
git push origin feature/quiz-app          ← all 3 go to GitHub at once
⚠️
Common mistake

Many people think committing means their work is backed up online. It is not. Until you push, your commits exist only on your machine. If your laptop dies, unpushed work is gone. Push before you close your laptop.

4

Branching — Why and How

A branch is a separate, isolated copy of your code where you can work without touching the main stable code.

# Without branching — all work on main, risky
A ── B ── C ── D ── E (half-done feature, main is broken!)

# With branching — main stays safe
A ── B ── C ── D ──────────────── G  ← main (always stable)
                   │                  │
                   └── E ── F ─────────┘  ← feature branch (merged in)
📌
The Golden Rule

main = always working code. Never commit directly to main. Always: branch → work → merge.

When is a branch required?

SituationWithout BranchWith Branch
Building a new feature Unfinished code is in main Work isolated, main untouched
Urgent bug fix needed mid-feature Half-done code is in the way Switch to main, fix, come back
Something breaks everything Hard to undo Delete the branch, main is fine
Two people on same project You overwrite each other Each person has their own branch
Code review before merging Reviewing live broken code Review the branch via Pull Request 
# Create a branch and switch to it (one command)
git checkout -b feature/my-new-component

# See which branch you are currently on
git branch

# Switch to an existing branch
git checkout main

# Delete a branch after it has been merged
git branch -d feature/my-new-component

The Complete Workflow — Step by Step

☁️
Clone the repo GitHub → Local

Download the repository from GitHub to your machine. Do this only once per project.

git clone https://github.com/username/repo-name
📥
Pull latest main Local

Before starting any work, always get the latest code from GitHub. This ensures you start from the most up-to-date version.

git checkout main git pull origin main
🌿
Create a new branch Local

Never work on main directly. Create a branch named after what you are building. This branch exists only on your machine for now.

git checkout -b feature/my-new-component
✏️
Write your code Local

Edit your files normally. Use Ctrl+S as usual. Git is watching but not doing anything yet.

📋
Stage your files Local

Tell Git which changed files you want to include in the next commit. You can add specific files or all files.

git add force-app/main/default/lwc/myComponent/myComponent.js OR to add all changed files: git add .
💾
Commit — save a snapshot Local

Save the staged files as a checkpoint in your local history. Write a clear message describing what you did. You can make many commits before pushing. GitHub does not know about these yet.

git commit -m "Add score calculation logic to quiz app"
🚀
Push branch to GitHub Local → GitHub

Send your branch and all its commits up to GitHub. Now your work is backed up online and visible on GitHub. Use -u on the first push for this branch.

git push -u origin feature/my-new-component
🔀
Open a Pull Request Manual — on GitHub website

Go to github.com and open your repository. GitHub shows a banner: "feature/my-new-component had recent pushes." Click "Compare & pull request." Write a title and description of what your branch does. Click "Create pull request." This is NOT automatic — you do this manually on the GitHub website.

👀
Review and Merge Manual — on GitHub website

On a team, someone reviews your code. Solo, you review it yourself. When satisfied, click "Merge pull request" on GitHub. Your branch's code is now part of main.

🔄
Update local main + clean up Local

Pull the updated main to your machine. Delete the feature branch locally since it has been merged.

git checkout main git pull origin main git branch -d feature/my-new-component

Writing Good Commit Messages

Bad Messages

  • "random changes"
  • "new changes"
  • "fix"
  • "wip"
  • "aaaaaa"
  • "added a variable"

Good Messages

  • "Add score calculation to quiz app"
  • "Fix searchName casing in SOQL query"
  • "Remove unused RefreshEvent import"
  • "Add Lightning Message Service component"
  • "Fix search input not clearing on reset"
✅
Formula for a good message

Start with a verb. Say what changed. One line. Past or present tense consistently.
Add [what]  ·  Fix [what]  ·  Remove [what]  ·  Update [what]

⚠️
Commit size — one concern per commit

Don't bundle 6 unrelated file changes into one commit. Each commit should represent one logical change. It makes it easy to understand history and undo specific things if needed.

All Commands Reference

Command What it does Where
git clone <url> Download a repo from GitHub to your machine. Run once per project. GitHub → Local
git status Show which files are changed, staged, or untracked. Local
git checkout -b <name> Create a new branch and switch to it in one command. Local
git checkout <name> Switch to an existing branch. Local
git branch List all local branches. The * shows which one you are on. Local
git add <file> Stage a specific file — add it to the next commit. Local
git add . Stage ALL changed files at once. Local
git commit -m "msg" Save staged files as a snapshot in local history with a message. Local only
git log --oneline Show the commit history in a compact one-line format. Local
git push -u origin <branch> Upload your branch and its commits to GitHub. Use -u on first push. Local → GitHub
git push origin <branch> Push again after the first time (no -u needed). Local → GitHub
git pull origin <branch> Download latest commits from GitHub to your local machine. GitHub → Local
git branch -d <name> Delete a local branch after it has been merged. Local
git diff Show what has changed in your files since the last commit. Local

Ctrl+S vs git commit — Not the Same Thing

PropertyCtrl+Sgit commit
How oftenEvery few seconds while typingWhen a logical piece of work is done
MessageNoneRequired — you describe the change
HistoryOverwrites the previous saveKeeps every version permanently
Can go backNo — only the latest existsYes — to any commit ever made
ScopeOne fileMultiple files at once
✅
Rule of thumb for when to commit

Not after every line. Not after hours of work. Commit when one thing is complete — a function works, a bug is fixed, a component is built. Keep doing Ctrl+S constantly as you type — that is unrelated to Git.

Quick Reference — The Loop

// complete workflow — repeat for every feature

# ── SETUP (only once per project) ──
git clone https://github.com/username/repo
# ── START EVERY FEATURE ──
git checkout main
git pull origin main
git checkout -b feature/your-feature-name
# ── SAVE WORK (repeat as you code) ──
// edit your files ...
git add path/to/changed/file.js   // stage specific file
git commit -m "Describe what you just did"
# ── PUSH TO GITHUB ──
git push -u origin feature/your-feature-name
# ── PULL REQUEST (manually on github.com) ──
// Go to github.com/username/repo
// Click "Compare & pull request"
// Write title + description → Create pull request
// Review → Merge pull request
# ── CLEANUP AFTER MERGE ──
git checkout main
git pull origin main
git branch -d feature/your-feature-name
🔁
The short version — memorise this loop

pull main → create branch → write code → git add → git commit → git push → open PR on GitHub → merge → pull main → delete branch → repeat
